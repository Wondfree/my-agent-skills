# Calibration examples

Read when the trigger, evidence threshold or permission boundary is unclear. These are fictional scenarios, not instructions to access a service or run an experiment.

| Request or situation | Apply the skill this way |
| --- | --- |
| “Move a cloud report job to a laptop because reports are missing.” | Trigger: establish whether output delivery is the real problem; compare retaining the service and repairing delivery before migration. |
| New shared data collector or monitoring service | Trigger: compare existing project capability, official interfaces, maintained open source and suitable managed services before custom collection. |
| Routine null-pointer fix or small adapter for an approved dependency | Handle directly with existing code and relevant checks; no full discovery or renewed route decision. |
| “Use only the existing SDK; add no dependencies.” | Honor the fixed constraint. Advisory alternatives do not reopen the approved route. |
| Add a small utility dependency | Assess actual impact. A narrowly scoped addition does not automatically require an ecosystem survey; new access, service costs or shared maintenance can make the choice consequential. |
| Optional knowledge catalog has no match | Continue relevant official/open-source discovery or disclose access gaps; no match does not justify self-build. |
| Proposed custom task queue or retrieval store | Trigger: review build-versus-reuse evidence before committing to a new shared capability. |
| Documentation establishes that a storage API accepts JSON | Reuse that capability evidence. Inspect actual account permissions when relevant; do not create a test resource merely to re-prove documented support. |
| A scheduled job already passed write/read-back | Reuse that evidence for its recorded conditions. Check state recovery across runs only when the outcome requires it; stop when sufficient. |
| An automated intake saves work items, but approved downstream research still needs manual launch | The delegated outcome is incomplete. Investigate and repair the existing handoff within scope; do not add per-item approval to already delegated research. |
| An agent is authorized to research and save drafts | That scope does not authorize changing authoritative project records, extending permissions or performing consequential transactions. Preserve applicable approval gates. |
| Production database migration has official upgrade support | Retain environment-specific backup, restore and migration checks under the appropriate authorization. |
| A new project requests shared infrastructure | Trigger, but inspect that project's rules. Do not assume another project's knowledge catalog, approvals or runtime configuration is available. |
